# おへや（アイソメ風ぷに部屋）— CONCEPT

状態：2026-11-09 オーナーが方針を承認（A案で開始）。
この文書は「何を作るか・なぜそうするか」の元。設計書（`docs/superpowers/specs/`）と食い違ったら、設計書を直してからここに反映する。
公開リポジトリに入る文書なので、子どものなまえ・育成データなどの個人情報は書かない。

## 1. 目的
ホーム画面を「アイソメ風のぷに部屋」にして、次の3つを足す。
1. ぷにが部屋の中で、勝手にいろいろな動きをする
2. 現実のお世話で貯めた「ぷにコイン」で、家具やかざりを買って置ける
3. ずかんのぷにを部屋に呼べる（部屋でいっしょに暮らす）

## 2. 決定事項（2026-11-09 オーナー承認）
| 項目 | 決定 |
|---|---|
| 描画方式 | **A案**：今の構成のまま（ビルドなし・依存なし・CSP は `'self'` のみ）で Canvas 2D のアイソメ。Three.js は入れない |
| 将来の土台 | 段階1の関門のあと・段階2の前に TypeScript＋Vite への移行（C案）を検討する。そのため、純ロジックは DOM に触れない ES モジュール＋JSDoc の型で書く |
| ぷにの見せ方 | 3D 化しない。既存の正面向き SVG（`petSVG`）を「立て看板」として床に置き、左右反転で向きを出す |
| 家具の絵 | コードで組んだ SVG（`art.js` と同じ方式）。面ごとに明暗をつけて立体に見せる。オリジナルデザイン |
| ホーム画面 | ホーム画面そのものを「おへや」にする（別画面にしない） |
| コイン | 新通貨「ぷにコイン」（名前は仮）。成長の `pts` とは別に持つ（`pts` を使うと進化の条件が戻ってしまうため） |
| コインの入り方 | 報告時に `FOODS[food].pt` と同額。ぐんぐんたいむの倍率はかけない（等倍）。**付与は `report()` の1か所**（将来の `acceptBoxEvents` も同じ関数を通す） |
| ずかんのぷに | 部屋に呼べる数は部屋の広さで決まる（6×6=2匹、8×8=4匹、10×10=6匹） |
| 子ども向け配慮 | 呼んだぷには病気にも空腹にもならない。部屋が汚れる・家具が傷むなどの罰要素は入れない |
| 作業の置き場所 | **作業ブランチ `feature/oheya`** で進める。GitHub Pages は `main` がそのまま公開され、子どもが毎日使う本番に直結するため、段階1の関門（G1）が済むまで `main` に入れない |
| 実機確認（段階0） | **Mac 上で直接** `python3 -m http.server 8000`（devcontainer の外・リポジトリ直下）を起動し、iPad の Safari から `http://<MacのIP>:8000/dev/room-spike.html` を開く（同じ Wi-Fi）。Service Worker は https でしか動かないので、オフライン動作の確認はしない。描画・発熱・タッチの確認が目的 |
| 段階0のあと | 結果を報告して**止まる**。実機の滑らかさ・発熱を見て、A 案のまま段階1へ進むかを私が判断する |
| 部屋の雰囲気 | **パステルの絵本風の洋室**。今の背景（空・丘）とぷにの色調に合わせ、家具は丸みのあるかわいい形 |

## 3. 画面と描画の仕様
- **投影**：2:1 のアイソメ。タイル 64×32（論理 px）。`sx=(gx-gy)*32`、`sy=(gx+gy)*16`。部屋は奥の壁 2 面＋床。初期は 6×6、買い足しで 8×8・10×10。
- **背景の層**：床・壁は一度オフスクリーンに描いてキャッシュする。窓の外は時間帯（`band()`）の空（`sceneSVG` を流用するか簡略化）。
- **深度**：物の足元の `(gx+gy)` が小さい順（奥から）に描く。ぷにも家具もこの順で混ぜて描く（ぷにが家具の裏に回り込める）。
- **ぷにの絵**：`petSVG` の文字列 → `data:image/svg+xml` → `Image` にして、`(form, face, arms, 状態)` ごとにキャッシュ。CSP の `img-src 'self' data:` で通る見込み（段階0で確認）。
- **更新**：`requestAnimationFrame`。目安 30fps。タブが裏・ねんね中は止める。`prefers-reduced-motion` のときは動きを控えめにする。
- **夜**：ゆっくり暗くする（明滅・急な点滅は使わない）。ランプを持っていれば、まわりをやわらかく光らせる。
- **タッチ**：主役のぷにの上に、透明な `#pet` ボタンを重ねて毎フレーム位置を合わせる。今のなでなで・ぎゅー・れんだ・あたまの判定コードをほぼそのまま使い、アクセシビリティも保つ。呼んだぷには、タップで `FORMS[f].say` のひとことと、`voice` に合わせた鳴き声を出す。
- **Canvas のサイズ**：`devicePixelRatio` を考慮し、幅・高さは JS から設定する（インライン `style=""` は書かない）。

## 4. ぷにの自律行動
- 行動は **`js/room-ai.js`（DOM に触れない純粋ロジック）** に置く。乱数は引数で注入し、テストで固定できるようにする。
- **基本の行動**：たちどまって呼吸、ぽてぽて歩く、きょろきょろ、ぴょん、ダンス、ねんね。
- **家具を使う行動（段階4）**：すわる（ソファ・ラグ）、ねる（ベッド）、あそぶ（ボール）、よむ（本棚）、みる（窓・植物）、たべる（ちゃぶだい）。
- **主役の状態との連動**：顔と腕のポーズは既存の `look(S, ctx)` をそのまま使う。おなかが空いているとトレイのほうを向いてしょんぼり、病気のときはベッドか床で休む、夜は `asleep()` に従って寝る。キャラは死なない。
- **歩き方**：床のマスを BFS で結び、マスの間はなめらかに補間する。手足のアニメは作らず、つぶれて伸びる・弾む・傾く、で「ぷにっと」見せる。
- **ぷに同士**：近づいて手を振る、ハートが出る、あとをついていく（段階3）。
- **性格づけ（案、段階3）**：形ごとの「得意なつよさ」（かしこさ→本棚、げんき→ボール、ほかほか→こたつ、きれい→鏡）で行動の重みを変える。`FORMS[f].hint` と `rules.js` の分岐表から引ける見込み。
- **時間帯**：朝はのび・窓、昼は遊ぶ、夕方はごろごろ・ごはん、夜はねんね。

## 5. データ設計（段階2から。段階1では保存形式を変えない）
保存形式 `v:2` は据え置き、**キーを足すだけ**。足したら `DEF()` と `sanitize()` の両方に入れる。
- `coin`：整数 0〜999999
- `own`：`{アイテムID: 個数}`。ID は `ITEMS`（`js/room-data.js`）にあるものだけ。個数 0〜99
- `room`：`{n:6|8|10, floor:ID, wall:ID, items:[{id,x,y,r}], guests:[形ID]}`
  - `items` は最大 60 件、`r` は 0〜3、置き場所は床の範囲内で足あとが重ならないもの（重なったら後ろを捨てる）
  - `guests` は `S.zukan` に含まれる形だけ、数は部屋の広さの上限まで
- `undo` の各項目に、もらったコイン額 `c`（0〜20）を足す。取り消しではコインも戻す（0 未満にはしない）
- 世代交代で引き継ぐ：`coin`・`own`・`room`
- バックアップコードの上限（40,000 文字）に収まること（部屋のデータは数百バイトの見込み）
- 読み込み・復元は必ず `sanitize()` を通す。ID・座標・個数はすべて検証する

初期の品ぞろえ（案・値段は仮、実機で調整）：ゆか・かべ（各30）、ベッド（60）、ソファ（50）、ラグ（25）、ほんだな（40）、ちゃぶだい（30）、ぼーる（15）、かんようしょくぶつ（15）、らんぷ（20）、ぬいぐるみ（10）、まどかざり、おへやをひろげる（200）。
1 日に貯まるコインは最大およそ 20、ふつうは 10〜15。品ぞろえは入れ替えて消さず、増える一方にする。

## 7. 守る約束（`CLAUDE.md` との対応）
1. 静的サイトのみ・ビルドなし・依存なし → A 案で維持（`package.json` を作らない）
2. 外部通信なし・CSP は `'self'` のみ → Canvas と `data:` 画像だけで完結
3. インライン script／`style=""`／`onclick=""` なし → サイズや位置は JS から設定
4. 入力値は `esc()` ／ `textContent`
5. 保存データは `sanitize()` を通す
6. 旧データを読めるようにする（足すだけ）
7. UI の文言はひらがなのみ（家具やおみせの名前もひらがな）
8. キャラは死なない・罰なし
9. オリジナルデザインのみ（既存キャラの模倣をしない）
10. `sw.js` 以外を変えたら `sw.js` の `VERSION` と `app.js` の `APP_VERSION` を上げ、新しい `js/*.js` は `ASSETS` に足す

## 9. 未決・リスク
- 実機での描画の滑らかさ・発熱・バッテリーは、コンテナ（GPU なし）では測れない。段階0・1 の実機結果だけを根拠にする。
- 実機確認の方法：決定済み（§2）。Mac 上で直接サーバーを起動して iPad から見る。ホーム画面に追加した状態の挙動は見られるが、Service Worker（https のみ）は確認できない。
- 純ロジックの単体テストは、Node 標準の `node:test` を想定（依存・`package.json` なし）。devcontainer の Node が `package.json` なしで ES モジュールを読めるかは**未確認**。読めなければオーナーに相談する（`package.json` を勝手に作らない）。
- 呼んだぷにの数を増やすほど描画コストが増える。段階0で上限を測る。
- 報告の取り消しは日をまたぐと消える。コインも同じ扱いにする（案）。
- C 案（TS＋Vite）へ移行する場合：保存キー `punipuni-nikki-v2`・形式 `v:2`・バックアップコード（`PUNI2:`）を維持し、往復テストを書く。公開先（GitHub Pages のままか、Cloudflare Pages か）は別判断。`CLAUDE.md` の約束 1〜3 を改訂する。
